Sovereign AI Taxonomy & Ontology — Course Model v1.0

Status: Course-authored conceptual model; not an ISO standard, legal classification, regulatory requirement, or vendor certification.
Reviewed: 2026-11-17
Maintainer: Course authors; changes require a definition and example, impacted modules and evidence of acceptance.

Why the distinction matters

A taxonomy puts concepts into meaningful classes or hierarchies. An ontology says what entities exist, which properties belong to them, and which relationships between entities are meaningful. A control catalogue lists requirements/tests, while an evidence graph shows how claims can be verified. None of these constructs alone proves legal compliance or sovereignty.

Tool Question it answers Example
Taxonomy What kind of thing is this? A processing workload is regulated, customer-facing, personal-data-bearing.
Ontology How do things relate? A ProcessingActivity uses a Dataset, runsOn an InfrastructureService, and isGovernedBy a LegalInstrument.
Control catalogue What must be enforced or assessed? Prohibit unauthorized administrative access to prompt logs.
Evidence graph What supports the asserted control? An access test and signed log export verify a particular policy.
Maturity model How capable is the organization? Documented → implemented → tested → monitored → independently assured.

Course-level sovereign AI taxonomy

These are independent classification axes, not a single mutually exclusive ladder:

  1. Scope: national / sectoral / enterprise / individual workload. A workload can belong to an enterprise in a regulated sector.
  2. Control dimension: territorial / operational / technological / legal-contractual. An assessment may show different levels across dimensions.
  3. Deployment pattern: public / managed sovereign / private / hybrid / air-gapped / edge. A deployment label alone says nothing about actual control.
  4. AI stack layer: facility / power / accelerators / compute / network / storage / data / model / runtime / application / IAM / governance / operations.
  5. Autonomy posture: external dependence / contractual controls / customer-held keys & privileged operations / independently operated / independently reproducible. Illustrative course rubric, not an official scoring standard.
  6. Evidence strength: marketing claim / contractual statement / configuration screenshot / repeatable technical test / independent attestation. Context and age can change evidentiary value.

Legal and compliance sub-ontology (Module 05)

LegalJurisdiction is not synonymous with geographic server location. A business may have overlapping regulatory exposures determined by establishment, activity, customers, data subjects, sector, contracts, and actual law. ApplicableRequirement is not inferred from a country label alone.

Invariants for a credible compliance/control graph:

  • Every assertion of legal applicability has a named human reviewer, authoritative source and recorded rationale; missing information means unresolved, not “compliant.”
  • Every Requirement points to a specific LegalInstrument version and article/section.
  • Each Control points to a responsible owner and a repeatable Test or an explicitly noted evidence gap.
  • Evidence is time-bound and proves only the tested claim in the named environment.
  • A residency test cannot prove a provider’s privileged-access posture or defeat lawful disclosure in another jurisdiction.
  • Control and Requirement are different types. Business preference is not silently upgraded to a legal obligation.

Worked example — a hypothetical UAE enterprise

Scenario (not a legal finding): A UAE enterprise runs a document assistant; prompts are processed in a UAE data center, while the vendor can remotely administer its logs.

  • Taxonomy: scope = enterprise/workload; deployment = managed/private; territorial controls = partially evidenced; operational control = unresolved; legal position = requires counsel.
  • Ontology: Workload → ProcessingActivity → Dataset; Vendor → supports → InfrastructureService; Control → tested by → Test → produces → Evidence.
  • Decision: ask the provider for documented privileged paths and a restricted-support test. Do not label the platform fully sovereign based on region alone.

Evidence confidence labels

VERBATIM_SOURCE (short checked quote) / PRIMARY_SOURCE_PARAPHRASE / VENDOR_REPORTED / COURSE_INFERENCE / SIMULATED / NOT_VERIFIED. Each chapter should expose these labels when ambiguity matters.

Versioning and governance

Breaking changes to classes/properties/relations: bump major version and review linked modules. Vocabulary additions: minor version. Editorial corrections: patch. Machine-readable illustrative entities live in ontology.yaml; do not confuse the YAML schema with a production knowledge graph or legal rules engine.
